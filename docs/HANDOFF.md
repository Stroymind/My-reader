## 0. 五分钟交接摘要

**目前是什么：**「我的书房」已经是一个网页版 / PWA + Capacitor Android 共用界面的离线优先电子书阅读器，主要面向移动端。仓库包含书籍导入、阅读、进度、书签、高亮和摘录等实现，以及 GitHub Pages 与 Android 构建流程。

**长期想做什么：**保留轻量阅读体验，探索「阅读 → 积累 → 理解 → 应用」的个人知识工作台。用户尤其重视 Windows **桌面无背景阅读**（文字如桌面的一部分、自动适配背景对比度、低干扰、连续阅读）。该桌面体验目前是**产品方向和待验证原型**，不能写成仓库已经实现的功能。

**现在先做什么：**验证现有 Web/Android 构建与核心阅读流程，修复 EPUB 空白、文字重叠、导航与进度问题，形成稳定演示版本；再隔离探索 Windows 桌面模式。AI 知识库、知识图谱和商业化不属于当前必须交付的范围。

**必须优先排查的静态风险：**“scripts/sync-www.mjs” 的文件同步清单未包含 “bilingual.js” 与 “epub-repair.js”，但应用 JS 模块存在对应导入。若 Android 打包仍使用该清单，可能因缺失模块而启动失败。此问题尚未通过实际 Android 构建确认。

## 2. 已有代码：事实与边界

以下“存在”仅说明**在代码/README 中能找到实现或声明**，不代表本轮测试已经通过。

| 模块 | 已观察到的实现 | 关键文件 |
| --- | --- | --- |
| 网页 UI | 书架、整理、导入、阅读视图、设置及摘录弹层 | index.html、app.css、app.js |
| 文件导入 | EPUB / PDF / TXT / HTML；ZIP 批量导入；同书去重逻辑 | importer.js |
| EPUB | epub.js 阅读引擎；尝试修复路径、编码、XHTML；DRM 检测 | engines.js、epub-repair.js |
| PDF | PDF.js 解析与页面展示 | engines.js、vendor/ |
| 文本阅读 | 文本解析、排版和位置管理 | engines.js、settings.js |
| 阅读记录 | 书籍、文件、进度、高亮、书签等 IndexedDB 存储 | db.js、app.js |
| 中英对照 | 当前页翻译与本地缓存；代码调用第三方在线翻译服务 | bilingual.js |
| 离线能力 | Service Worker 缓存静态资源 | sw.js、manifest.webmanifest |
| Android | Capacitor 8 共用 Web 资源并生成原生 APK | capacitor.config.json、android/ |
| 自动化 | 浏览器冒烟测试；APK 构建；Pages 部署 | scripts/、.github/workflows/ |

**重要区别：**
- **已实现代码路径** ≠ **已经经过验收**。用户曾反馈某些 EPUB 导入后空白、文字挤在一起、翻页/导航不正常，应列为待复现缺陷。
- **当前跨平台** = Web / PWA + Android；不要把它称为已经完成的 Windows 桌面原生应用。
- **阅读数据本地保存**与**翻译请求本地执行**不是一回事。bilingual.js 会将需要翻译的页面文本发送到外部服务；需要明确的隐私说明及失败处理，不应宣传“所有内容永不离开设备”。

关键协作约束：
1. 改动任何模块导入路径，要同时更新 Android 的 Web 资源同步清单与 Service Worker 静态缓存清单。
2. “www/” 是自动生成目录（被 .gitignore 忽略），不要直接把它作为源码编辑。
3. “tweet-to-text/” 是仓库中独立工具，不得因整理目录而删除或使其页面失效。
4. 数据库名为 “shufang”，当前 DB_VER 为 2；对象存储包括 books、files、meta、xlate。升级 Schema 前必须设计兼容迁移和回滚。

## 4. 本地启动、测试和构建

以下命令来自仓库内容；**尚未在本次交接实际执行**。

### 4.1 Web 开发验证

    npm ci
    python3 -m http.server 8765

然后在浏览器访问 http://127.0.0.1:8765/ 。应使用 HTTP 本地服务而非直接打开 file:// 页面，以便验证模块、Service Worker 和 IndexedDB 行为。

### 4.2 冒烟测试

    npm run test:smoke

脚本 “scripts/smoke.mjs” 会生成测试样书并使用 Puppeteer 进行浏览器检查，涵盖导入、高亮、复制、摘录、书签、刷新持久化、EPUB/PDF 和离线等流程。

**运行前约束：**该脚本目前使用 python3、硬编码 Chrome 路径 “/usr/bin/google-chrome”，并向 “/opt/cursor/artifacts/” 输出截图。它更像 Linux 环境下的专用测试脚本，Windows 本地执行可能需要适配。不要将“有测试脚本”写成“测试已经通过”。

### 4.3 Android 构建

README 声明所需环境：Node.js 22、JDK 21、Android SDK 36。

    npm ci
    npm run cap:sync
    npm run android:release

APK 目标位置为 “android/app/build/outputs/apk/release/”；GitHub Actions 会把安装包作为 “shufang-android” 构件上传。

在执行 release 前，必须确认同步后的 www 目录存在所有 JS 模块和资源；重点核查 “www/bilingual.js” 与 “www/epub-repair.js”。

### 4.4 发布

Pages 工作流目前在推送 main 时运行；Android 工作流在 main 推送、PR 和手动触发时运行。不要将仅用于文档的变更解释为功能已经发布或 Android 包已通过安装验证。

## 6. 产品方向（新共识，不是现状）

**一级目标：稳定的阅读体验**  
保证可靠导入、正确排版、阅读导航、阅读进度和基本摘录。无 AI 时也必须正常阅读。

**差异化实验：Windows 桌面无背景阅读**  
探索文字直接融入 Windows 桌面的阅读方式：无固定白底、无厚重边框、工具按需浮现、根据真实桌面背景保持文字对比、连续滚动、字体大小变化时重新排版而不是整体缩放裁切。不要未经论证直接更换已有 Web/Android 技术栈。先做单独的 Windows 技术可行性原型（窗口层级、交互穿透、对比度、输入焦点、跨桌面环境行为），再决定集成路线。

**后续价值延伸：**
- 阅读 → 划线、批注、摘录、导出；
- 积累 → 检索、整理与来源定位；
- 理解 → 可选 AI 解释、问答、总结；
- 应用 → 面向实际任务的知识工作流。

这些是阶段假设，不构成一次性开发清单。尤其不要现在就做知识图谱、复杂 Agent、云端社区或通用知识库商城。

## 7. 建议实施路线与停止条件

### Phase 0｜建立真实基线（最先执行）

- 记录 git 分支、提交 SHA、运行环境及依赖。
- 启动 Web，检查 Pages 地址，并运行现有冒烟测试；留下结果和失败日志。
- 构建或至少执行 Android 资源同步，验证上述模块缺失风险。
- 建立最小格式样本集：EPUB2、EPUB3、异常 EPUB、TXT UTF-8/GBK、文本 PDF、扫描 PDF、HTML、ZIP。
- 把事实、推断、未知状态分别记录，形成缺陷清单。

**门禁：**未得到真实运行证据，不宣布“已交付稳定版本”。

### Phase 1｜修复核心阅读

- 先处理 Android 静态资源同步与启动故障（如实测成立）。
- 针对 EPUB 空白/乱码/排版问题建立失败样本与回归。
- 修复翻页、章节跳转和进度恢复。
- 对字号、行高、边距调整执行回归，不允许“放大后文字跑出屏幕”。
- 保护已有书籍、进度和摘录数据。

**门禁：**代表性样本稳定可读；核心操作无阻断；已有记录不丢失。

### Phase 2｜差异化阅读原型

- 保持 Web/Android 主线稳定。
- 通过独立原型验证 Windows 桌面透明阅读与动态可读性。
- 若成本、兼容性或交互质量不达标，可以暂停桌面模式；不要牺牲已有阅读能力。

**门禁：**可演示、可连续阅读、不妨碍基本桌面操作。

### Phase 3｜公开开发与用户反馈

- 展示实际使用过程和真实局限，而非功能概念图。
- 招募至少 5 名愿意认真试用的陌生用户作为初期目标。
- 记录具体问题、发生频率、现有替代方案、实际试用行为；不要把点赞视为购买证据。
- 每轮只对最重要的问题做小范围实验。

**门禁：**存在真实用户反馈和可追踪的产品迭代依据。

### Phase 4｜知识积累（需需求证据）

先验证批注/摘录/检索/导出等最小闭环。保留原文位置锚点和开放格式迁移能力，不急于构建复杂知识管理界面。

### Phase 5｜AI 增强（可选）

仅在用户真实需要时，增加基于当前文档的解释和问答；提供来源定位、失败状态与数据授权。AI 不得成为阅读核心的必要依赖，不强制使用付费 API。

## 8. 数据、隐私和兼容性不变量

1. 用户书籍、阅读进度、书签、批注不得因升级静默删除。
2. IndexedDB 版本变更须有备份、迁移、回滚及兼容性测试。
3. 不随意上传全文；对在线翻译等向第三方发送文本的能力必须提供清晰说明。
4. 在无网络时，已导入书籍的核心阅读能力应可用；需要网络的翻译/AI 能力必须明确降级。
5. EPUB 正文位置锚点、PDF 页码和文本位置应尽可能可追溯，以便未来稳定绑定摘录。
6. 不为了“统一格式”而损坏 PDF 固定版式；固定页渲染和可重排文本应保留不同策略。
7. 严格保留 “tweet-to-text/” 和现有发布入口；新增桌面试验不要影响移动端发布。

## 9. 给下一位开发 Agent 的执行协议

**先读：**README.md、package.json、index.html、app.js、engines.js、importer.js、epub-repair.js、db.js、bilingual.js、scripts/、.github/workflows/ 和本文件。

**第一条任务：只读审计**。输出当前 SHA、可运行入口、真实功能、测试状态、缺陷证据和最小修改提案。不要未经审计重构整个项目。

**执行规则：**
1. 一个可验证的问题对应一个小修改或 PR；先写失败用例，再修复，再回归。
2. 明确区分“静态发现”“成功复现”“已修复”“自动测试通过”“设备验收通过”。
3. 修改导入/渲染逻辑后，至少回归 EPUB、PDF、TXT、HTML 及已有持久化数据。
4. 不更改仓库所有者、Android 签名/包名、Pages 域名或数据结构，除非有明确需求与迁移方案。
5. 任何 AI / 云端功能默认可关闭，不得引入强制登录和强制付费服务。
6. 没有验收证据不得把计划中的 Windows 桌面模式、知识图谱、AI 问答写入“已完成”。

**每轮开发应交付：**
- 改动摘要及涉及文件；
- 已执行命令及输出；
- 通过 / 失败 / 未运行的测试清单；
- 已知风险和回滚方法；
- 下一步最小任务。
